### 1) Registro de cliente + confirmación de email ✅
- Capturas: `01-registro-01-pagina-confirmado.png`, `01-registro-02-login-post-confirmacion.png`
- Se creó una cuenta en estado **no confirmado**, se obtuvo el **link/token real**
  de confirmación y se abrió `/auth/callback` → `verifyOtp` → **`/auth/confirmado`**
  ("CUENTA CONFIRMADA"). El campo `email_confirmed_at` pasó de `null` a un
  timestamp y la cuenta pudo **autenticarse** después.
- **Aclaraciones honestas:**
  - La tienda **no tiene UI pública de registro** — el modelo es *guest checkout*
    (comprar sin cuenta); `/login` es solo del panel admin. Se ejercitó la
    **infraestructura real** de signup + confirmación (callback + verifyOtp +
    página de confirmado), que sí existe y funciona.
  - El signup público de Supabase está topeado por el **rate-limit del SMTP por
    defecto** (`mailer_autoconfirm` off). Por eso la cuenta se provisionó vía
    admin API en estado pendiente y luego se confirmó con el flujo real.
  - La **entrega** del email no se verificó (no hay acceso a un inbox).

## Bug encontrado y CORREGIDO (migración 007)

> **Estado: RESUELTO.** Se corrió `007_orders_update_grant.sql` en el SQL Editor y
> se re-verificó el flujo por UI: la orden pasa de **"Pendiente de pago" → "En

### 3e) Cambiar el estado de una orden desde el panel admin (era ❌, ahora ✅)
- Capturas: `03-admin-11-e-lista-ordenes.png`, `03-admin-12-e-orden-detalle.png`, `03-admin-13-e-orden-actualizada.png`
- **Síntoma:** en `/admin/ordenes/[id]` se elige un estado y se aprieta
  "Actualizar", pero **el estado no cambia** (vuelve a "Pendiente de pago"). Falla
  **en silencio** (sin mensaje de error).
- **Causa raíz (confirmada):** el rol `authenticated` **no tiene `GRANT UPDATE`
  sobre `public.orders`**. La acción `updateOrderStatus` (`lib/admin/actions.ts`)
  usa el cliente del request (rol `authenticated`) y Postgres rechaza el UPDATE
  con `42501 permission denied for table orders` **antes** de evaluar la RLS. La
  acción no chequea el error → el form "actualiza" pero nada cambia. Es el mismo
  tipo de bug que arregló la migración 006, pero **006 cubrió products/variants/
  categories/discounts y se olvidó de `orders`**.
- **La seguridad NO se relaja con el fix:** la policy `orders_admin_all`
  (`for all using public.is_admin()`) ya existe; solo falta el grant de tabla.
- **Fix listo:** `supabase/migrations/007_orders_update_grant.sql`
  ```sql
  grant update on public.orders to authenticated;
  ```
  Hay que **correrlo en el SQL Editor de Supabase** (igual que la 006). Después de
  eso, el cambio de estado de órdenes funciona. *(No se pudo aplicar
  automáticamente: las migraciones DDL se corren a mano en el SQL Editor.)*
